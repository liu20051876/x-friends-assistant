## X 页面悬浮窗

授予 X 页面权限后，打开任意 x.com 页面，右侧会出现蓝色悬浮球，并自动展开悬浮窗。悬浮窗里就是完整工作台（与侧栏同一套数据），收起后回到悬浮球，点击悬浮球再次打开。

- **悬浮球**：拖动可移动，松手吸附到最近的左右边缘；单击打开悬浮窗。
- **悬浮窗**：拖标题栏移动，拖右下角调整大小（最小 340×420），双击标题栏恢复默认位置和大小。位置、大小记在本机，下次打开沿用。
- **标题栏按钮**：「自动展开」开关（关闭后打开 X 只显示悬浮球，所有标签页同步）、改在侧栏打开、收起为悬浮球。
- 工作台在第一次展开时才加载；收起只是隐藏，再展开时停在原来的标签页。
- 扩展自己开的后台工作标签（发送、时间线采集、原创发布、读主页、读名单）**不显示悬浮球和悬浮窗**，避免遮挡页面或抢走输入焦点；这些标签记在 `storage.session`，浏览器关闭即清空。
- 实现：`floating.js` 由 background 在权限授予后以 `xfa-ball` 注册为内容脚本（沿用 0.4 的 id，覆盖旧注册），刚授权/安装时会注入已打开的 X 标签；悬浮窗用 iframe 加载 `dashboard.html?embed=1`，因此 manifest 增加了仅对 `https://x.com/*` 开放的 `web_accessible_resources`。工作台样式移到 `dashboard.css`，侧栏与悬浮窗共用。

## 原创草稿触发器

两条原创帖之间的间隔在设定的分钟数之间随机（默认 **180–480 分钟**，即 3–8 小时），到点**无条件**调用已配置的 AI 服务生成英文原创草稿，与回复数量完全解耦：回复失败或暂停不影响原创节奏。到期时间记录在 `nextDueAt`，浏览器关闭期间错过的时间会在下次启动时补处理，并由独立 alarm（`xfa-original-due`）唤醒休眠中的 service worker。调整间隔从下一轮生效。

面板顶部有「自动生成原创草稿」开关：**关闭后闹钟立即清除、不再自动生成或推进重试**，已有草稿、间隔设置和到期时间全部保留；重新打开后从下一轮到期时间继续。暂停期间仍可手动审核、发布已有草稿。

**生成后先过硬规则**（`auto-review.checkOriginalDraft`）：12–280 字符、必须英文（含中日文直接拦）、无链接/@/话题标签、无 AI 自述、不少于 4 个英文词。不合格的不入库，标为失败并写明原因，可一键重试生成。

每条原创帖需点击「审核并发布」并再次确认账号及全文才会发送。发布在后台 compose 标签进行，成功判定有三类信号：成功 toast、页面导航离开 `/compose/`、编辑器或表单消失（后两者要求连续两次轮询确认，防止重渲染误判）——因为 X 经常不弹 toast，只关编辑器。发布结果仍不确定时，必须先到 X 核实，不能直接重试；用户核实后在面板上点「已发布/未发布」，标签随即回收。

生成失败可手动重试；扩展中断时请求可能已经产生费用，需人工确认后重试。compose 标签与发送工作标签一样有崩溃清理，浏览器重启后遗留标签会被自动关闭。原创草稿只保留最近 50 条。旧版按回复条数计数的状态会平滑迁移：保留已有草稿和待核实记录，下一条从迁移时起按新间隔随机。

X（Twitter）好友互动半自动工具。核心思路：**机器做采集和起草，机器先按硬规则筛一遍，人只处理没过的那些，最后一公里点一次就整批推进**。

每天 30 条经过校验的精品回复，胜过 1000 条模板刷屏。

## 时间线采集

工作台「采集时间线」按钮：在隐身后台标签打开 `x.com/home`，**默认先走接口嗅探**，拿不到才退回滚动。两条路子共用同一套过滤、同一套审核与发送，只是取数据的方式不同。

### ① 接口嗅探 + 主动翻页（默认）

X 首页每加载一屏会自己发一个 `/i/api/graphql/<id>/HomeTimeline` 请求，一次返回约 20 条结构化数据。`timeline-sniff.js` 在页面主世界（`world: "MAIN"`，`document_start`）包住页面的 `fetch`，把这份响应原样存下来：

- **首屏那份响应就等于「一条都不用滚就有 20 条候选」**
- 目标更多时，用页面自己发过的请求模板带 `cursor` 连翻，请求间隔取设置里的随机区间（默认 3–6 秒）
- 模板有两种形态都要认：**POST**（`fetch(url, {method:'POST', body})`、`fetch(new Request(...))`，或 body 是 Blob/FormData/URLSearchParams——后几种异步读出文本再记模板，改 `variables.cursor` 再发，body 变长所以 `content-length` 必须删）；**GET**（首页时间线也可能走这种，游标与 features 都编码在 URL 的 `variables` query 里，直接改写 URL 重发）。只认 POST 字符串 body 就会「响应拿到了、模板是空的、一页都翻不动」
- **模板一次都拿不到时**（请求没被包到）：不自己造请求，改成让页面滚一屏、只吸收它新发出的那份响应——渲染那部分慢动作省掉，只留解析 JSON；步长 0.7 屏、每步最多等 6 秒，连续 5 步都没有新响应才停
- **重放被拒时**不整批作废：403/401/400/404/422 基本都是缺少按请求计算的 `x-client-transaction-id`，记下状态码后放弃重放、切到「页面自己滚、只读响应」继续攒；只有 **429** 是真被限流，立刻停手
- 数据来自接口而不是 DOM：正文、作者、浏览数、`lang` 语言标签、能否回复、是否广告、游标都在，`nostatus`/`noviews` 那类损耗基本消失，长文也不会被截断
- `x-csrf-token` 每次从 `ct0` cookie 重取，不沿用模板里的旧值
- 429 立刻停手，不再继续翻页，已拿到的部分照常入队
- 任何一步失败（没捕获到响应、接口改名、注入失败）都返回失败，自动**退回滚动采集**，诊断串前面带 `fallback=<原因>`

一次请求失败或目标条数已经够了，就不会再发第二次——不会为了凑数硬翻。页数上限按 `目标条数 / 12 + 2` 估（过筛后大约剩一半），最高 16 页。

### ② 滚动采集（兜底）

在隐身后台标签打开 `x.com/home`，按 0.7 屏步长（480–840px）滚动，把首页 feed 渲染出的卡片解析成候选。帖子 id 取卡片自己的 `/handle/status/id` 时间戳链接（排除引用帖里的嵌套链接），不依赖用户名区是否已渲染完成。**只排除广告和阿拉伯文帖，其他热帖都收（不再限制作者是否在互关名单里）**：浏览量直接读动作行柱状图旁的数字（支持 `3.6M`/`1.2万`/`1,234` 单位换算），读不到浏览数的新帖不碰、低于门槛的不互动；广告（Promoted/`placementTracking`）、阿拉伯文帖、回复按钮不可见的卡片过滤；纯转发、引用帖都保留，目标是外层作者。名单只在显式传入时才当作范围限定，面板默认不传。

三个可调参数在面板上直接填写并记住上次值：**目标条数**（合格候选攒够就停，默认 20）、**浏览量门槛**（默认 500）、**最多滚动屏数**（默认 30，只对滚动兜底生效）。合格判定在页面层先算一遍用于提前停止，background 侧仍会再校验一遍。

**设置页的两个新开关**（`xfa-config-v1` 的 `tlFast` / `tlGapMin` / `tlGapMax`）：

- **优先用接口嗅探采集**：默认勾选。取消勾选就固定走滚动，适合想对比两条路子，或在接口被限流时先降级。
- **翻页请求间隔**：默认 3–6 秒，可填 1–60 区间内的 最短/最长。每次主动翻页前在这个区间里随机取，越慢越不容易触发限流。它只管「翻页请求」，和发送回复的 15–120 秒间隔是两套。

风险面要说清楚：嗅探本身只是读页面已经发出去的响应，和现在没区别；但**主动翻页**意味着请求节奏由脚本决定，而不是「滚到哪儿就拉哪儿」。HomeTimeline 有速率限制，打急了会 429，账号也可能被标记。所以默认 3–6 秒、单次最多 12 页、失败即刻停手——这些不是可选项，是刻意留的刹车。

入队条目带 `source: 'timeline'` 标记（名单采集为 `roster`），队列卡片显示来源；之后的草稿生成、自动过审、人工确认、15–120 秒随机发送、成功后点赞、日上限 30、工作时段与暂停全部沿用，**不区分来源、先到先得**。采集与发送互斥，发送流程运行中不能采集。

**采完整批自动发送**：面板上的「采完整批后自动发送已过审的」默认勾选并记住上次值（`xfa-tl-opts-v1` 的 `autoSend`）。勾上时，采集结束先生成草稿，然后把队列里**所有已过审条目**（时间线与名单两类都算，先到先得）直接开跑，省掉点「开始发送」这一步；随机间隔、日上限、工作时段、连败暂停仍然由后台把关，任一条不满足就不启动并在状态行写明原因。取消勾选则回到原来的手动点按钮节奏。

后台标签渲染慢，等待采用自适应：每次滚动后最多等 6 秒、每 0.5 秒复查一次新卡片，**连续 5 轮既没有新卡片、页面高度也没增长才判定刷到底**，避免把「还没渲染」误判成结束。滚动步长按视口 0.7 屏（480–840px）：首页卡片常是长文加大图，一张两三千像素，小步长会在同一张卡里空滚十来次。发现新卡片后**多等一拍（0.5 秒）并补扫一次**，让这一屏画完再走——否则只看到一张新卡就跳，会漏掉同屏还没渲染出来的卡片。测定「停顿」时按**无进展距离**累计，走满 2 屏仍没有新卡片且页面高度不变才记一次停顿，长卡片不会再被误判成刷到底。滚动用「固定步长 + 把最后一张卡贴到视口底部」双保险触发懒加载，但贴底补滚限幅在 0.35 屏以内、且只补「已大半在视口里」的卡——否则一张 2400px 的长卡会让它一次跳两屏多，把中间那张卡甩出渲染窗口。状态行附带诊断串（**嗅探成功时**是另一条更短的串）：

```
articles unique hit tgt dup nostatus arab views noviews vlow norow notRoster
scrolls stalls dist pos dom skel h vis fp
```

含义依次为：累计卡片数、唯一 id 数、合格候选数、目标条数、重复数、解析不出 id 数、阿拉伯文帖数、读出浏览数、读不到浏览数、低于门槛数、动作行缺失数、名单外数（只在显式传了名单时才可能非零）、滚动屏数、停顿轮数、累计滚动距离、当前位置/总高、单轮同时存在的卡片数（虚拟列表窗口）、加载占位数、页面高度最小-最大、标签可见状态、首张卡结构指纹。`dist` 与 `h` 一起看最直观：`dist` 很大而 `unique` 很小，说明卡片很高、步长吃掉在单卡里；`skel` 常驻非零且 `h` 不涨，才是真的拉不动；`vis=hidden` 只用于辅助判断，实测后台标签也能正常拉取；`fp` 缺区块说明 X 改版。

**嗅探模式的诊断串**：`mode=sniff tpl=<POST模板0/1> get=<GET模板0/1> pages=<页数> reqs=<主动请求次数> nudges=<让页面自己滚的次数> replay=<重放被拒次数> st=<最后一次HTTP状态> cards=<条数> cursor=<有没有下一页> post=<观察到的POST次数> getreq=<观察到的GET次数> reqobj=<靠Request对象取模板的次数> body=<原始body类型 string/Blob/FormData/URLSearchParams/...> err=<失败原因>`。`pages` 把首屏那份也计入，所以 `pages=1 reqs=0` 表示「一页都没翻，全靠首屏那次响应」；`getreq>0 get=1 reqs>0` 表示正在用 GET 模板翻页；`replay=1 st=403` 表示重放被拒、已切到页面自滚；`nudges>0 reqs=0` 表示模板没拿到、走的是「页面自己滚、只读响应」；`post=0 getreq=0` 则说明请求根本没被包到；`body=` 用于判断非字符串 body 到底是哪种类型。失败退回滚动时，滚动那条诊断串最前面会多一个 `fallback=<原因>`，例如 `fallback=没有捕获到时间线接口响应`、`fallback=ST=429`、`fallback=嗅探超时`。

阿拉伯文帖按**文字系统**判：阿语系字母（`Script=Arabic`，涵盖阿拉伯语、波斯语、乌尔都语）占全部字母的一半以上就判为阿语帖，采集层就丢掉——好友链路在 `filter-rules.js` 的 `filterPosts` 里拦，时间线链路两条路都判：嗅探路径直接用接口给的 `legacy.lang`（`ar`/`fa`/`ur`/`ps`/`sd`/`ckb`/`ug`），缺 lang 时再按字形算；滚动路径在 `timeline-page.js` 解析卡片时打 `arabic` 标记并排除出合格候选。判据只算字母、不算数字与符号，所以纯数字帖、emoji 帖不会误判；中文或英文帖里夹带一句 `السلام عليكم` 也不会被误伤（判的是自己的正文，不是引用段）。

## 工作流

```
结构化读取关注列表 + 粉丝列表（被动接收 X 自身请求，不重放）
   → 关系字段判定互关；字段缺失时用粉丝集合差集补
   → 互关名单 / 未回关名单写入名单工作区
   → 逐个打开好友主页，本地只读采集
   → 筛选：7 天内 / 原创或引用转发 / 每人 1 条 / 关键词 / 剔除阿拉伯文帖
目标帖入队
   → 立即送云端生成回复草稿（硅基流动 / DeepSeek 可切换）
   → 多道校验：格式 / 语言（仅英中）、长度 / 链接@# / 与原帖重合度 / 重复草稿 / 同人当日重复
合格 → 自动过审，进「待发」　　不合格 → 留在队列等你确认（Enter 通过 / S 跳过 / E 编辑）
   → 点一次「开始发送（整批推进）」
自动打开帖子 → 输入回复 → 发送 → 验证成功 → 点赞 → 关闭标签
   → 随机 15–120 秒间隔，每日上限 30 条，可随时暂停
```

**全程不调用 X 官方 API**，名单靠结构化读取，帖子靠 DOM 只读，发送靠页面模拟，零 API 成本。

## 使用顺序

侧栏顶部是常驻状态栏（今日已发 / 待确认 / 待发 / 需核实 / 发送状态，点数字直接跳到对应队列），下面分四个标签页：**工作台**（采集 + 回复队列 + 发送）、**名单**、**原创**、**设置**（AI 服务、发送节奏、危险操作、演示模式）。首次使用时工作台顶部有「开始之前」清单，按顺序完成即可。X 页面授权只有一个入口：状态栏的「授权 X」，授权后自动隐藏。

**① 获取名单**

在「名单」页填写你的 X 用户名，点「读取关注列表」。

工具会打开关注页，优先使用页面自身的请求配置进行只读分页；无法取得请求配置时会自动滚动并接收页面数据。读取到结束信号或无法继续时停止，请核对数量和完整性。

**读取在后台进行**：标签以 `active: false` 创建，不会切到你眼前、不抢焦点，全程不滚动不点击，读完（或你点停止）自动关闭。侧栏里有一条进度条，分母取页面顶部显示的关注总数，显示「已读取 N / 总数 人（百分比）」；页面顶部数字没解析到时退化为不确定态，不假装有百分比。

如果「状态未知」不为 0，可以点「读取粉丝列表」补充判定。粉丝列表未确认读取结束时，找到的账号可以判为互关；未找到的账号仍保留未知状态。

读取完成后同一面板立即显示：

- 关注总数 / 明确互关 / 未回关 / 状态未知
- 完整度提示（与页面显示数量比对）
- 与上次读取的差异（新增关注 / 不再在列表）

**已经手上有两份 CSV 时**，展开面板里的「手动导入 CSV（备用路径）」，分别导入完整关注和未回关，得到同样的互关结果，这一步不需要授权读取 X 页面。

两个导出按钮：**导出未回关 CSV**、**导出互关 CSV**。

**② 确认名单**

在同一个面板核对人数，勾选「我确认名单所属账号及来源」。这一勾是采集的前置条件，名单只在本地处理。状态未知的账号不会进入互关候选。

**③ 采集与发送（同一个面板）**

填本批好友数量（自由填写，≥1 的整数，上次填的值会记住）和时间窗口，点「开始采集」。超出名单人数时按名单人数推进。逐浏览器标签打开好友主页读取帖子，按规则筛选后入队。游标自动保存，下次接着上次的位置轮询。

**采到一个就立刻生成草稿**：每读完一位好友，采到的帖子马上送云端生成回复，不必等整批跑完。面板上四格数字：本批入队 / 待审 / 自动过审待发 / 今日已发。

**草稿的语气来自账号本人的真实回复**：`ai-service.js` 里放了一组该账号真发过的短回复当风格锚点（极短、口语、爱玩梗），提示词要求模仿它们的**节奏和句长**，但禁止逐字照抄。同时每次生成会随机挑一个「回应角度」（只回应一个细节 / 一句反问 / 说自己的类似感受 / 轻微调侃 / 接梗 / 短判断词加半句），避免一批 20 条全长成同一个句型。

**先判语境再开口**：提示词的第一步是判断原帖在干什么——报喜、吐槽、提问、发资讯还是玩梗，回复必须顺着同一个方向走。报喜的帖子不许唱反调、不许「但是」、不许泼冷水；拿不准说什么意思时，宁可说一句明显站在对方那边的话，也不要去抖机灵。同时禁掉三类最容易露机器的写法：**对偶反差金句**（「A 容易，B 难」「不是 X 而是 Y」「看似 X 其实 Y」）、结尾总结、祝愿式收尾，以及「确实 / 不得不说 / 总的来说」开头；并规定不许把原帖的圈内词（进池 / 流量池 / 破圈 / 上热门）按字面拧成负面意思。

**④ 自动过审的判定标准**

以下每一条都满足才自动过审，否则落回待审并标出原因：

| 检查项 | 要求 |
|---|---|
| 来源 | 必须是云端生成（模板兜底的一定要人看） |
| 语言 | 只允许英文 / 中文 / 日文；出现俄文、韩文、阿拉伯文等其他文字系统直接拦下。**而且必须与原帖同语种**：中文帖回英文、英文帖混中文、日文帖没有假名，全部判为需人工确认 |
| 格式 | 无链接、无 `@` 提及、无 `#` 话题标签、无「As an AI」这类自述 |
| 长度 | 回复 4–240 字符（允许「典」「神了」这类真人短反应，两个字的纯语气词仍算过短）；纯英文需 4–45 个词且以句末标点结尾。原创帖仍是 12 字符起 |
| 超短限额 | 不超过 10 字符的回复，一批最多 5 条自动过审，多出来的回落人工——短回复本身更像真人，堆满一批就像刷屏 |
| 内容 | 不能等于或大段复述原帖（重合度过高会拦） |
| 去重 | 不能与队列里已有草稿完全相同；名单来源同一好友当天只有一条能自动过审，**时间线来源不受这条限制**（只要求同一批内同一账号不重复），因为它本来就可能扫到当天已经互动过的好友 |

**⑤ 人工确认（只处理没过的）**

队列分三栏：**待你确认** / **待发** / **需核实**。`Enter` 通过，`S` 跳过（5 秒内可撤销），`E` 编辑草稿，方向键切换，草稿框按 `Ctrl+Enter` 也可通过、`Esc` 退出编辑。焦点在按钮或链接上时快捷键不生效，Enter 留给按钮本身。每条卡片上会写「✓ 自动过审」或「未自动过审：原因」，草稿框旁有字数计数（4–240）。

已通过的条目可「撤回到待确认」。失败条目可「重新加入待发」；结果待核实的条目先「查看原帖」到 X 核实，再选「已在 X 看到回复」（计入今日已发）或「确认没发出，重新加入待发」，两者都需二次确认。

通过后修改草稿会恢复为待你确认，需重新通过。正在发送的帖子不能编辑或跳过；「重新生成未过审草稿」只处理待审条目，并保留生成期间发生的人工修改。

**⑥ 发送**

点一次「开始发送（整批推进）」。之后程序按间隔逐条打开帖子、发送回复，在识别到明确的成功提示后尝试点赞。**单条失败不再打断整批**：某一条失败只记在该条上，流程继续按随机间隔推进下一条；只有连续 5 条失败才会自动暂停（连续失败通常说明账号受限、权限失效或页面改版，继续跑只会连错）。若发送结果无法确认（`uncertain`），该条留在队列等你核实，整批同样继续。停止任务会阻止后续发送，当前已经开始的帖子会继续处理到结束。

**原帖已被删除或不可用**（X 在同一地址只渲染一句「This post is unavailable」，或把地址重定向走）会被单独认出来：该条标记为「已跳过」并从队列归档（同时记入历史，之后不会再被采集到），整批继续推进。这类失败不等 25 秒页面加载超时——页面一完成加载停在别的地址就立刻判定，省掉空等。

发送与采集用的是**同一套滚动做法**，但步长更克制：`behavior: instant`（不做平滑动画，动画在后台标签里既慢又会被合并），一步只走 0.4 屏（约 320px），跳完立刻检查，不用定时猜。步长不给大是有原因的——一步跨太远会跳过还没渲染的区域，而 X 的虚拟列表**不会回补**被跨过的内容，表现就是「翻页太快，按钮反而不见了」。

找按钮的顺序是：先在原地找 → 不在就把**帖子底部挪进视口**（长帖的操作栏、内联回复框都在那儿，不必盲扫）→ 还找不到才向下小步扫 → 最后退回帖子顶部用 150px 更小的步子重走一遍。触底不代表没内容，到底会先等一会儿；位置和高度连续三次都没变化，才判定真的没有更多。

身份判断分两层：**路由（地址栏 pathname）是权威门**，开头精确匹配 `/{handle}/status/{id}`，不匹配直接中止，绝不操作；**article 内的 status 链接是定位手段**，按 status id 全文匹配（含 `/quotes` 等子路径），引用帖的 id 不同天然被排除。如果路由已确认、但页面上的链接都对不上（X 某些版本焦点帖不渲染自身 permalink），就退回首篇 article 的按钮，而不是直接放弃；点赞同样走这个兜底。

发送用的标签是**整批共用一个后台标签**：第一条开一次（`active: false`，不抢焦点），之后逐帖只改这个标签的地址，不再每帖开关一个——标签栏不会一条接一条地闪。页面必须确认落到目标帖上才继续执行（等 URL 与加载状态都对上），批结束或你点停止时自动关闭。浏览器崩溃遗留的标签会在下次启动时清掉。

发送开始时会在队列里留下「处理中」标记。若浏览器崩溃、扩展被重载或后台被系统回收，重启后该条会被标记为失败并提示「先核实、勿重试」，不会自动补发，避免同一条回复发两遍。

## 风险边界（请务必读完）

**1. 这不是「合规」，是「低风险」**

X 服务条款明确禁止未经书面同意的爬取和自动化访问。DOM 模拟点击同样在禁止范围内。本工具靠「人审 + 小规模（每天 30 条）+ 随机间隔 + 分散在工作时段」把实际被识别的概率压到很低，但这不构成合规保证，也不改变条款本身。账号风险由使用者承担。

**2. 上限设置**

500 条/天在数学上需要 9 小时以上，且行为画像必然异常。500 应当作**月度总量**而不是日上限。默认 30 是经过权衡的数值。

**3. 名单读取的实现边界**

`graph-reader.js` 在 MAIN world 观察 `fetch` 与 `XHR`。快速模式使用页面自身的请求配置和分页游标发起只读请求；快速模式不可用时通过滚动触发页面加载。读取器有 90 秒 lease，`stop()` 会还原原始函数。这仍属自动化访问，不会改写关注数据。

**4. 选择器依赖**

`data-testid` 与 graphql 路径（`/graphql/<hash>/Following`）都是 X 的内部约定，前端改版会让读取或发送失效。哈希值是动态的，代码用后缀匹配而不是写死完整路径。每步都有明确报错，不会静默乱发。

**5. 以下部分我无法在本地验证，需要你在真实环境首次试跑确认**

- 关注/粉丝页的 graphql 响应结构是否仍为 `data.user.result.timeline`，用户对象是否仍带 `relationship_perspectives.followed_by`；
- 页面顶部关注数的文案格式（`1,234 Following` / `1.2万 正在关注`）解析是否命中；
- 帖子页的 `[data-testid="reply"]` / `tweetTextarea_0` / `tweetButtonInline` 是否与当前版本一致；
- 输入框四重兜底（execCommand → paste → beforeinput → textContent）中哪一路有效；
- X 页面当前语言和版本的成功提示是否能被识别；无法确认时会停止，需人工核实；
- 点赞按钮 `like` 与 `unlike` 的状态切换是否可观测。

**建议第一次先只读名单、再采集 3–5 条、手动通过 1 条试跑**，确认全流程通了再放开批量。

**6. 后台标签可能被节流**

默认在后台标签执行发送，Chrome 会限制后台页的定时器和渲染，可能提高失败率。若连续失败，到配置里勾选「发送时把工作标签切到前台」。滚动已改成 `instant` 跳转 + 状态检查，不再依赖动画帧，被节流的影响比早期版本小，但仍不是零。

**7. 间隔精度**

Chrome 对 `alarms` 有调度粒度限制，短间隔用 `setTimeout` 精确触发、`alarms` 兜底唤醒。15 秒这类短间隔在 SW 被系统回收时可能延后到 40 秒左右。

**8. 自动过审改变了风险结构，请留意**

原来每条草稿都过一遍人眼，现在只有没通过校验的才需要你看。省了人力，但**行为侧没变安全、反而更像脚本**：一批回复在程序控制下连续发出，比逐条手动点更像自动化行为。所以下面三条约束比以前更重要，不要为了省力调高：

- 日上限保持 30（上限 50）；
- 间隔保持 15–120 秒随机，不要压到 15 秒定值；
- 工作时段保持白天，别让它在凌晨跑。

另外建议前几批先看一遍自动过审的条目，确认校验器没有把明显不合格的放过去（比如语气跑偏、答非所问——这类硬规则查不出来，只能靠人扫）。
